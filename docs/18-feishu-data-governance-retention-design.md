# DeepAuto Agent：飞书数据治理与保留策略设计

## 1. 本阶段结论与边界

本文件基于当前代码和 Prisma schema 的静态盘点，定义飞书接入后续的数据治理实施门槛。它不是已批准的保留政策，也不构成地域、合同或法定保留期限的结论。

当前仓库没有按工作区配置的保留期限、legal hold、清理 worker 或已获批准的删除期限。因此本阶段**不新增**定时删除、TTL、批量 purge、归档导出或“加密擦除”实现。未经合规负责人明确批准期限、适用地域、审计保留要求和 legal hold 规则前，任何自动清理都必须保持关闭。

本设计适用于飞书消息入口、Worker 中的 Lark 资源工具，以及它们写入的数据库记录；不把飞书权限申请文档或计划中的工具能力视为已经上线的数据处理能力。

## 2. 已盘点的数据边界

| 数据类别 | 当前存储位置 | 当前保护或用途 | 治理风险与约束 |
| --- | --- | --- | --- |
| 入站任务指令 | `Invocation.instruction` | 以原始文本持久化；同时用于来源事件幂等和执行输入关联 | 可能含用户正文；在无批准期限前不得清理。删除会削弱问题追溯与事件去重证据。 |
| 飞书消息身份与会话定位 | `LarkMessage` 的应用、租户、会话、消息及发送者字段 | 用于身份冲突检测、回复投递和工作区约束 | 是入站去重和投递状态机的锚点；不能由调用方传入的内部 ID 替代。 |
| 最终回复 | `LarkMessage.finalText` | Worker 在写入前以工作区和 invocation 绑定的上下文加密 | schema 字段名不表示密文语义；后续迁移或报表不得把它当作明文输出。 |
| 工具写前快照与提供方结果 | `LarkToolOperation.snapshotEncrypted`、`providerResultEncrypted` | 用于写入幂等、结果判断与 `UNKNOWN` 排查；内容已加密 | 不得写入 AuditEvent 或日志；未决写入不能删除。 |
| 飞书用户 OAuth 凭据 | `LarkUserConnection` 的 access/refresh token 密文字段 | 连接工作区成员、租户和 scope，凭据已加密 | 凭据、刷新状态和 scope 不得进入模型 prompt、审计 metadata 或治理报表。 |
| 写入二次确认 | `LarkWriteConfirmation` | 服务端重新核验角色、会话、目标哈希与过期状态 | 未过期、未消费或未失效的记录属于活跃安全状态，不能被清理破坏。 |
| 审计事实 | `AuditEvent` | 按工作区、动作和时间检索 | `metadata` 仅能保留最小事实；禁止正文、原始 webhook、令牌、加密材料或外部原始响应。 |

上游模型传输是独立的数据边界：当前已授权飞书任务的 `instruction` 会作为 agent prompt 输入；被授权读取的 Docx/Base 正文可以作为同一任务的工具结果进入模型上下文。身份、令牌、原始 webhook 和未获授权的资源正文不得进入该边界。后续若引入模型供应商、区域或零保留承诺配置，必须由工作区受控配置和服务端策略决定，不能依据消息内容或模型自行选择。

## 3. 清理前必须保留的运行态与关联

清理的首要目标不是压缩表行，而是不破坏幂等、权限重验、回执和 `UNKNOWN` 的安全处置。

以下任一条件成立时，关联的 `Invocation`、`LarkMessage`、`LarkToolOperation`、写入确认和最小审计事实都不得进入 purge 候选集：

1. 消息处理仍为 `QUEUED`、`CLAIMED` 或 `WAITING_PR`，或处理/投递状态为 `UNKNOWN`；
2. acknowledgement 或 final reply 仍为 `PENDING`、`CLAIMED` 或 `UNKNOWN`；
3. 工具操作仍为 `CLAIMED` 或 `UNKNOWN`，或存在未完成的外部写入核验；
4. 写入确认尚未过期，或尚未被消费、失效或由事务明确终结；
5. 关联 Job、Attempt、callback、恢复案件或 legal hold 尚未达成服务端可证明的终态；
6. 仍处于该来源事件的去重窗口，或删除会让同一飞书事件失去可验证的幂等依据。

`Invocation` 对 `LarkMessage` 和 `LarkToolOperation` 存在级联关联，且飞书消息以应用、租户和消息组成唯一键。因此未来的删除顺序必须先在事务内验证候选对象的工作区、身份来源和终态，再按已设计的依赖关系处理；不能用“孤儿行扫描”、跨工作区批量 ID 或仅凭创建时间直接删除父记录。

审计与业务正文必须分离处理。即使业务数据已经符合删除条件，也只能按已批准的审计政策保留最小、不可含敏感正文的审计事实；不能为方便保留审计而复制指令、回复、工具快照或凭据。

## 4. 未来保留策略的实施门槛

在实现任何清理代码前，合规、法务和安全责任人必须为每个工作区或受控策略组确认以下输入，并以版本化、服务端可审计的配置落库：

- 数据类别的保留期限、起算事件、适用地域和客户合同要求；
- 审计事实与安全调查材料的独立保留期限；
- legal hold 的创建者、授权角色、覆盖范围、解除流程和优先级；
- 用户删除请求、客户终止、工作区删除与备份恢复之间的处理顺序；
- 上游模型供应商、传输地域、训练/保留条款及允许输入的数据类别。

缺少任意一项时，策略解析结果必须是“不执行清理”，而不是回退到全局默认天数。工作区管理员不能通过消息命令、客户端携带的工作区 ID 或自行声明的角色绕开这些策略。

### 4.1 最小化 purge 工作流

获批后的首个实现应使用受控 Worker，而非 Gateway、模型工具或公开 HTTP 接口。最小流程如下：

```text
调度器选择已批准策略版本
  -> 服务端枚举单一 workspace 的候选记录（不接收调用方内部 ID 作为授权）
  -> 应用 legal hold、活跃状态、未知状态和关联终态排除条件
  -> dry-run 产出仅含数量、类别、时间窗口和不可逆摘要的报告
  -> 经独立授权后，按固定小批次重新读取并在事务中再次校验条件
  -> 删除允许删除的数据或按已批准方式去标识化
  -> 记录最小 purge 审计事实，不记录正文、令牌或原始 payload
```

dry-run 是强制门槛而不是日志级别：它不得执行外部副作用、不得解密快照或回复正文、不得在输出中列出消息文本、令牌、外部资源 URL 或内部记录 ID。实际批次必须可停止、可限速、可重试其数据库事务，但不得把 `UNKNOWN` 外部副作用重试为新的飞书写入。

如果政策要求“删除加密内容”，实现必须先由安全负责人明确密钥层级、备份、副本、恢复演练和可验证的销毁证据。不能把删除某一行或删除密钥引用宣称为已经完成所有副本的加密擦除。

### 4.2 legal hold 与删除顺序

legal hold 必须是服务端持久化的、工作区范围受限的状态，创建、变更和解除均要求可审计的授权身份。它优先于正常保留期和用户发起的删除流程；hold 生效时，策略计算必须拒绝该覆盖范围内的 purge。

在不存在 hold 且所有状态已终结的前提下，未来实现应先清除可删除的敏感业务正文和加密结果，再处理仅为这些正文服务的关联记录，最后才按独立政策处理审计事实。每一步均需防止留下可重新拼接正文的副本，且不得删除来源事件去重、未知状态调查或恢复核验仍需要的记录。

## 5. 验收条件

启用清理前至少满足以下验收：

1. 缺少工作区批准策略、期限、地域信息或 legal hold 判定结果时，Worker fail-closed 且不删除任何记录；
2. 跨工作区、伪造身份、已撤销成员及调用方传入内部 ID 的请求均不能扩大清理范围；
3. `QUEUED`、`CLAIMED`、`WAITING_PR`、`PENDING`、`UNKNOWN`、未决工具写入和活跃确认记录均被排除；
4. 并发 dry-run 与实际批次、状态刚转换、hold 刚创建及授权刚撤销时，事务重验仍阻止错误删除；
5. 审计、日志、指标、错误和 dry-run 报告均不含用户正文、原始 webhook、令牌、密钥、解密结果或提供方原始响应；
6. 已在真实飞书沙箱验证终态、未知状态、失败、撤销授权、网络中断和恢复后的行为，再考虑对生产工作区开启策略。

## 6. 本阶段交付与下一实施门槛

本阶段只提交数据清单、上游传输边界、保留阻塞条件和未来实施验收；没有修改数据库 schema，没有新增 API、Worker、TTL 或删除逻辑。

下一阶段的目标是在不产生外部副作用的前提下，制定真实飞书沙箱的端到端验收矩阵：覆盖身份 fail-closed、快速 ACK、单消费者租约、受控资源读取/写入、`UNKNOWN` 停止恢复以及本文件列出的数据最小化观测要求。只有在该矩阵和合规保留输入都获确认后，才可以评估实现策略配置或 purge Worker。

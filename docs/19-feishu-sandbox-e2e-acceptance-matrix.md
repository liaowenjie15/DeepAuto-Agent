# DeepAuto Agent：飞书沙箱端到端验收矩阵

## 1. 目的、结论与执行边界

本矩阵把当前飞书接入的静态实现拆分为可重复的自动化门禁和必须在受控飞书测试租户中完成的端到端验收。它不表示任何真实飞书事件、OAuth 授权、消息投递或资源写入已经在本仓库环境中执行并通过。

本阶段只交付验收设计，不启动 Gateway 或 Worker，不建立飞书长连接，不请求 OAuth，不发送消息，也不读取或写入真实飞书资源。执行实际矩阵前必须由拥有测试租户权限的负责人明确批准测试窗口、测试工作区、测试资源及允许的网络出口。

相关安全前提来自现有实现：飞书配置完整时 Gateway 必须同时具备 Redis；仅取得 Redis 租约的实例可接收飞书事件；身份、租户和工作区由服务端规范化及授权；Worker 负责后续 ACK、最终回复和受控工具调用。`UNKNOWN` 不是可自动重试的成功状态，数据保留策略也禁止删除未决记录。详见 `docs/17-feishu-unknown-recovery-design.md` 与 `docs/18-feishu-data-governance-retention-design.md`。

## 2. 执行前门禁

### 2.1 自动化门禁

每次候选版本进入沙箱前，须在不含真实凭据的环境中完成：

```bash
bun run typecheck
bun run test:unit
bun run lint
git diff --check
```

这些命令只验证代码、迁移生成及模拟依赖，不能代替真实飞书验证。当前与本矩阵直接对应的单元覆盖包括：租约持有/丢失/待命/Redis 初始不可用、入站事件 tenant 校验、持久化后由 Worker 投递 ACK、受权私有读取、写权限与 Base delete 二次确认、以及 `UNKNOWN` 投递审计。

任一门禁失败时，不得进入沙箱；修复必须回到同一门禁重新验证，不能通过手工操作绕过。

### 2.2 测试环境隔离

真实执行只能使用以下隔离资源：

- 经批准的非生产飞书测试租户与单独的自建应用/机器人；不得把生产 App ID、App Secret、用户 token 或生产群作为测试替代品。
- 专用的 DeepAuto 测试工作区、数据库和 Redis namespace；它们不得承载生产 invocation、OAuth 连接、审计或恢复案件。
- 最少两台 Gateway 实例、一个 Worker 实例，以及只包含测试人员的私聊和允许群；每一类写操作使用单独的测试 Docx/Base 资源。
- 预先创建的 `MEMBER`、`OPERATOR`、`ADMIN` 及未授权测试身份；其工作区成员映射和 tenant 均由服务端配置，不通过消息内容、客户端参数或数据库内部 ID 赋权。
- 由受控 secret manager 注入的 `LARK_*`、数据库、Redis 和模型配置；禁止把值写入 `.env`、终端录屏、测试报告、日志、Issue 或本文件。

执行前由负责人核对 Gateway 的飞书配置组完整、OAuth callback 地址合法、`REDIS_URL` 可用且与该测试工作区隔离。配置缺项或 Redis 不可用应被视为预期的 fail-closed 场景，而不是以临时默认值启动服务。

### 2.3 最小证据采集

每个用例只记录：用例编号、候选版本、测试工作区别名、开始/结束时间、通过/失败、状态转换摘要、审计 action 名称、已脱敏的错误类别和负责人。不得采集或转存消息正文、Docx/Base 正文、原始 webhook、token、密钥、OAuth code、外部响应完整 body、聊天/消息/用户内部标识符。

允许的核验方式为受权人员在测试租户 UI 中确认可见副作用，以及在测试数据库中以最小字段、只读方式确认工作区范围内的状态计数和 audit action。若检查需要展示解密内容、完整 metadata 或真实标识符，立即停止该检查并改用受控的最小化观测设计。

## 3. 验收矩阵

| 编号 | 场景与操作 | 预期安全结果 | 最小证据 | 失败后的动作 |
| --- | --- | --- | --- | --- |
| F-01 | 在配置中缺少飞书必填项，或完整飞书配置但缺少 Redis 后启动 Gateway | 配置解析失败；不创建飞书入口、不接受事件 | 启动结果仅显示通用配置失败类别 | 停止；不得补默认值或跳过 Redis。 |
| F-02 | 使用测试应用的事件路径验证 tenant 与预配置信息不一致、或必要 sender/tenant 身份缺失的情况 | 事件被拒绝；不创建 invocation，不调用模型、不发送 ACK/回复 | 拒绝计数及无新增副作用的状态计数 | 停止并修复身份规范化/配置；不得用配置值回填缺失身份。 |
| F-03 | 未映射为当前工作区成员的测试账号私聊机器人 | 服务端授权拒绝；不产生任务、OAuth 访问或出站消息 | 授权拒绝 action 和无新增任务计数 | 停止；不得把账号临时添加为高权限成员以“让测试通过”。 |
| F-04 | 在非允许群发送普通消息、未 @ 机器人的群消息，以及机器人自身消息 | 全部被准入层忽略；无 invocation、无模型调用、无出站消息 | 准入拒绝/忽略计数 | 检查群 allowlist 与 bot 自身身份；保持群资源隔离。 |
| F-05 | 已授权成员在允许群 @ 机器人，或在许可的私聊发送无敏感测试指令 | 仅创建一次任务；Worker 后续仅投递一次 ACK 与一次最终回复 | 飞书 UI 的单一回执及工作区范围内的单一状态链 | 停止；先排查消息唯一键、投递 claim 或重放来源，不手工补发。 |
| F-06 | 用同一条测试事件触发可控重投递或官方重试 | 保持单一 invocation/处理链；不会创建第二个模型任务或重复回复 | 幂等冲突路径和单一记录计数 | 停止；不得以删除历史记录来验证重放。 |
| F-07 | 启动两个 Gateway，再使当前持租约实例失去 Redis 租约 | 仅持租约实例建立入口；失租实例立即停止接收；待命实例不得并行创建入口 | 两实例生命周期摘要及每条测试事件的单一处理计数 | 停止；恢复 Redis 后重新建立受控租约，不允许双实例继续收事件。 |
| F-08 | 已授权成员请求已明确授权的私有 Docx/Base 读取，并由未授权成员请求同类资源 | 前者仅在其授权范围内进入工具/模型上下文；后者不读取资源、不调用上游模型获取私有内容 | 资源授权结果类别、模型调用是否发生的布尔摘要 | 停止；不得打印 prompt、正文或 token 来“证明”边界。 |
| F-09 | `MEMBER`、`OPERATOR`、`ADMIN` 分别尝试 Docx/Base 写入 | 只有服务端授权的写角色可进入确认流程；其他角色不产生外部写入 | 角色拒绝或确认请求 action；测试资源变更次数 | 停止；不得通过直接修改角色或绕过确认来完成用例。 |
| F-10 | 对测试 Base 发起 delete，并使用错误、过期、重复或不同会话的确认；随后用同一会话的正确二次确认 | delete 仅接受匹配且未消费的独立确认；确认只能消费一次 | 无敏感 payload 的确认状态转换及最终单一删除结果 | 停止；保留测试记录和审计，禁止重放 delete。 |
| F-11 | 在 ACK、最终回复或工具写入的受控故障点制造超时/连接中断 | 状态转为 `UNKNOWN` 或其他可证明终态；审计最小事实；不自动重新发送、重新写入或扩展权限 | 状态机摘要、对应 audit action、无重复副作用 | 停止；按 `docs/17-feishu-unknown-recovery-design.md` 的只读证据门槛处置。 |
| F-12 | 在 ACK 后、执行中和最终回复前分别重启 Worker | 已持久化状态可继续安全处理；不存在并发重复 ACK/回复/写入；无法判定时保持 `UNKNOWN` | 重启前后状态链及外部副作用计数 | 停止；不得用“再执行一次任务”掩盖重复问题。 |
| F-13 | 复核测试运行的日志、指标、审计 metadata 与运行报告 | 不含用户正文、原始 webhook、令牌、密钥、OAuth code、解密快照或提供方原始响应 | 经授权的最小化审查结果 | 立即撤销测试材料的非必要访问并修复观测；不将敏感样本复制到缺陷单。 |
| F-14 | 在测试库中尝试让尚未终结的任务、`UNKNOWN` 记录、活跃确认或工具写入成为“保留清理”候选 | 没有清理 Worker 时不发生删除；未来策略实现前仍以 fail-closed 为准 | 无删除操作及状态计数 | 停止；不得手动删除记录以清理测试现场。 |

F-11 的故障注入必须在专用测试边界完成：可以使用测试 transport、暂时断开测试网络或经批准的代理规则，但不得通过修改生产飞书权限、发送畸形 payload、重放真实用户事件或暴露请求内容实现。

## 4. 执行顺序与停止条件

1. 先运行第 2.1 节门禁，记录候选版本与结果；所有失败均阻断后续步骤。
2. 由测试负责人创建短时测试窗口，并确认第 2.2 节隔离资源、成员角色和 secret 注入全部有效。
3. 依次执行 F-01 至 F-07，先证明配置、身份、准入、幂等与租约安全，再允许任何模型或资源读取。
4. 只有 F-01 至 F-07 全部通过，才执行 F-08 至 F-10；写入测试仅使用专用、可恢复的测试资源。
5. 最后执行 F-11 至 F-14，并按第 2.3 节输出最小证据；不会因收集证据而读取或导出业务正文。

出现以下任一情况，立即关闭入口或停止测试 Worker，并保留最小化故障证据：身份/tenant 不一致却进入处理；单事件产生多次副作用；失租实例仍接收消息；未授权读取或写入发生；`UNKNOWN` 被自动重放；或发现敏感数据进入日志、审计、指标或报告。恢复测试前必须完成根因修复并从 F-01 开始重新验证。

## 5. 通过判定与后续目标

“沙箱验收通过”要求所有适用用例一次完整通过，且不存在上述停止条件。单元测试通过、飞书后台显示应用在线、收到一条回复或 API 返回成功，均不足以替代该判定。任何无法在沙箱中唯一归因的结果均为未通过，而不是可在生产环境继续观察的例外。

本阶段没有执行真实沙箱测试，因而没有任何 F-01 至 F-14 的通过结论。下一阶段的目标是由获授权的测试租户负责人准备隔离环境，并按本矩阵实际执行 F-01 至 F-07；在提供最小化证据且无停止条件前，不进入资源读写、故障注入或生产启用评估。

# C1：工作流健康巡检

## 目的

当 DeepAuto 拥有多条长期运行 workflow 后，自动汇总失败率、超时、连续失败、缺失定义和异常重跑，避免执行面静默退化。

## 价值与意义

- 将“某条自动化最近是否坏了”从人工逐条查看 Actions 历史变为可解释的运营信号。
- 可在用户发现任务没有运行之前，识别 webhook、Runner、依赖或权限的系统性问题。
- 为执行器容量和稳定性改进提供真实数据，而不是基于偶发事故扩张系统。

## 触发条件与前置条件

- 至少有 5 条长期运行 workflow，或单一 workflow 已出现重复的无声失败。
- Gateway 已将 Execution 与 GitHub run 建立稳定关联。
- 已定义“成功、失败、取消、预期跳过、降级成功”的统计口径，避免把正常取消算作故障。

## 实现方案

1. 从 GitHub API 和 DeepAuto 审计记录收集只读运行摘要。
2. 以连续失败、超时、失败率突增、定义缺失和 callback 未闭环为候选信号。
3. 报告先进入平台负责人可见的面板或飞书 thread，不自动创建 PR 或自动重跑。
4. 每项异常必须带 workflow、Execution、时间窗、失败类别和排除理由。

## 验收策略

- 人工制造超时、连续失败、预期取消和缺失 workflow 四类样本，分类正确。
- 任务不会因巡检本身失败而被误判为成功。
- 巡检只读 GitHub 和控制面数据，不领写仓库 token、不启动 Agent。

## 人工决策

- 何时从周报升级为实时告警；建议先周报，积累基线后再设阈值。
- 是否把不闭环的 callback 视为最高优先级故障；建议是。

## 当前不做原因

当前只有一个核心执行 workflow，先把其状态机和 callback 做对，再为它增加第二套巡检系统没有收益。

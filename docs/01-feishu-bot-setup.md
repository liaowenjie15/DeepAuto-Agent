# DeepAuto Agent：飞书机器人第一阶段搭建指南

> 创建日期：2026-10-18  
> 范围：仅完成“用户在飞书与 Agent 交互”的基础设施。本文不实现文档、表格、用户 OAuth、代码仓库、PR 或邮件自动化。

## 1. 第一阶段目标

完成下面这个最小闭环：

```text
用户私聊机器人，或在群内 @机器人
  → 后端收到飞书消息事件
  → 立即给消息加一个 reaction / 发送“处理中”提示
  → 异步调用 DeepAuto Agent
  → 在原消息的话题（thread）中回复最终结果
```

第一阶段的验收标准：

- 私聊机器人可以收到文本消息并回复。
- 群聊中只有明确 `@机器人` 的消息会触发 Agent。
- 机器人能立即给出“已接收”的可见反馈，不让用户等待时毫无响应。
- 最终回复落在原消息 thread 中，不刷屏到群主聊天流。
- 飞书重复投递同一事件时，不会重复启动 Agent。

## 2. 先确定的架构边界

不要在飞书事件回调中直接运行大模型、读写数据库、拉代码或发送邮件。推荐拆为四层：

1. **事件入口**：只接收飞书事件、去重并快速 ACK。
2. **快速反馈**：立即加 reaction，创建“处理中”消息或状态卡片。
3. **异步执行器**：把用户请求交给唯一的 Agent Worker 处理。
4. **出站回复**：将结果回复到触发消息所在的 thread，并更新处理状态。

这样做的原因：飞书事件有响应时限；若入口同步等待模型或工具执行，平台会重推事件，最终出现重复任务和重复回复。

## 3. 在飞书开放平台创建应用

### 3.1 创建企业自建应用

1. 使用有权限的飞书组织账号进入 **飞书开放平台**。
2. 创建一个 **企业自建应用**，名称建议为 `DeepAuto Agent`。
3. 设置应用图标、应用简介和负责人。
4. 在应用能力中添加 **机器人**。
5. 设置机器人名称和头像；名称应让用户知道它是内部 Agent，而不是普通群成员。

> 第一阶段先只对开发/测试成员开放。不要一开始就发布给整个组织。

### 3.2 获取 App ID 与 App Secret

在应用的“凭证与基础信息”页面获取：

- `App ID`
- `App Secret`

它们是后端使用 bot 身份调用飞书 OpenAPI、建立长连接的基础凭证。`App Secret` 只能放到密钥管理或部署环境变量中，绝不能提交到 Git。

## 4. 配置事件订阅：优先使用长连接

### 4.1 为什么选长连接

第一阶段选择 **长连接**，不使用公网 Webhook：

- 本地开发不需要公网域名或临时隧道。
- 后端主动连向飞书，减少回调验签、暴露公网接口等前置工作。
- 适合只有一个 Agent 调度实例的早期系统。

运行时约束：同一个飞书应用只应有一个长连接消费者。不要让多个可横向扩容的 API 实例同时启动长连接，否则会造成去重状态分裂、重复消费和重复回复。

### 4.2 订阅第一期事件

在“事件与回调”中：

1. 选择 **使用长连接接收事件**。
2. 添加消息接收事件：`im.message.receive_v1`。
3. 保存后创建应用版本，并发布到测试范围。

该事件足够支持：

- 用户私聊机器人。
- 用户在群内 `@机器人`。
- 接收文本消息并交给 Agent。

第一期不要订阅文档评论、卡片回调、日历、审批等事件；每增加一种事件，都增加新的准入规则和重复消费风险。

## 5. 申请最小权限

权限策略：**先让机器人能收消息、发消息和加 reaction；其它能力按工具逐项申请。**

### 5.1 第一阶段必须具备的能力

在“权限管理”中，为下列能力申请对应权限，并以飞书后台当前显示的权限名称为准：

| 能力 | 用途 | 第一阶段是否需要 |
| --- | --- | --- |
| 接收私聊消息 | 用户私聊 Agent | 是 |
| 接收群内 @机器人 消息 | 群聊调用 Agent | 是 |
| 以机器人身份发送消息 / 回复消息 | 发送“处理中”和最终答案 | 是 |
| 添加消息 reaction | 秒级确认已接收 | 是 |
| 读取机器人自身身份信息 | 获取并配置 bot open_id | 建议 |

权限字符串和可选范围可能随飞书后台版本变化。不要凭记忆批量勾选；每添加一个 API 或事件，在权限助手中确认该接口的最小权限要求。

### 5.2 暂缓申请的权限

以下能力暂不申请，等对应工具真实开发时再加：

| 后续能力 | 典型需求 |
| --- | --- |
| 创建/读取飞书文档 | 云文档读写权限 |
| 创建/更新多维表格 | Base/bitable 权限 |
| 查询组织成员 | 通讯录读取或搜索权限 |
| 用户私有文档、日历、会议纪要 | 用户 OAuth + 对应只读 scope |
| 文档评论 @机器人召唤 | `drive.notice.comment_add_v1` 事件、`docs:event:subscribe`、评论读写权限 |
| 读取其他机器人的群消息 | `im:message.group_bot_msg:readonly`；仅告警机器人场景需要 |

不要为了“未来可能会用”而提前申请高权限。权限应与已经实现、可审计的工具一一对应。

## 6. 发布、可用范围与测试群

1. 创建一个应用版本，将事件订阅和权限申请一起提交。
2. 在组织内发布到最小测试范围，例如开发团队或指定测试用户。
3. 新建一个测试群，将机器人添加到群内。
4. 约定群内规则：**只有明确 `@DeepAuto Agent` 的消息才是命令**。
5. 分别测试私聊和群聊两种入口。

群聊必须 `@机器人` 是重要的产品和安全边界：没有这个约束，Agent 很容易把成员之间的普通讨论误判为任务。

## 7. 后端环境变量

第一阶段建议建立 `.env.example`，但不填入真实密钥。实际值放在本机 `.env` 或部署平台的 Secret 管理中。

```dotenv
# 飞书企业自建应用凭证
LARK_APP_ID=cli_xxxxxxxxxxxxxxxxx
LARK_APP_SECRET=replace-with-secret

# 机器人在当前飞书组织内的 open_id。
# 用于群聊 @ 判断、过滤机器人自身消息；不要写入真实值到公开仓库。
FEISHU_BOT_OPEN_ID=ou_xxxxxxxxxxxxxxxxx

# 运行环境
NODE_ENV=development

# 以后接入 Redis / 数据库 / Agent Worker 时再增加：
# REDIS_URL=
# DATABASE_URL=
# AGENT_API_BASE_URL=
# AGENT_API_KEY=
```

变量职责：

| 变量 | 用途 | 安全要求 |
| --- | --- | --- |
| `LARK_APP_ID` | 初始化飞书 SDK，建立长连接 | 可视为标识符，但仍不要随意公开 |
| `LARK_APP_SECRET` | 获取 tenant access token，代表 bot 调用 API | 必须作为 Secret 管理，不能提交 |
| `FEISHU_BOT_OPEN_ID` | 过滤 bot 自己的消息、判断群聊是否 @ 到本 bot | 可配置在部署环境，不要硬编码 |

> Niuma 原项目使用的变量名是 `LARK_APP_ID`、`LARK_APP_SECRET` 和 `FEISHU_NIUMA_BOT_OPEN_ID`。DeepAuto 应使用自身命名，例如 `FEISHU_BOT_OPEN_ID`，避免把产品实现与原项目名称耦合。

## 8. 获取机器人 open_id 的方式

不要手写或猜测 open_id。推荐流程：

1. 先让长连接服务打印一条真实的群内 `@机器人` 事件。
2. 从事件消息的 mention / bot 相关字段中确认机器人 open_id。
3. 或使用飞书 OpenAPI 的应用/机器人身份相关接口查询，并将结果写入部署环境变量。
4. 将该值作为机器人自身身份使用：用于过滤自循环、校验群聊提及对象。

开发日志中可以短暂查看 open_id，但不要把完整事件原文、用户消息或 token 长期写入日志。

## 9. 代码实现顺序

按下面顺序实现，每步能独立验证后再进入下一步：

1. **SDK 连通性**：使用 `LARK_APP_ID` 与 `LARK_APP_SECRET` 建立长连接。
2. **消息事件日志**：仅打印脱敏后的 `message_id`、`chat_id`、消息类型和是否群聊；暂不调用模型。
3. **准入过滤**：忽略机器人自身消息；群聊必须检测到 `@bot`；私聊放行。
4. **幂等去重**：短期按 `message_id` 去重；生产环境再用 Redis 做跨实例去重。
5. **即时反馈**：先实现固定 reaction 或固定“已收到，处理中”线程回复。
6. **异步 Worker**：将消息封装为内部任务，调用唯一 Agent；入口不要同步等待。
7. **线程回复**：最终结果回复原消息，并确保落在原 thread。
8. **状态终结**：无论成功或失败，都更新“处理中”状态；禁止让用户看到永久卡住的状态。

## 10. 首次验收清单

完成第一阶段前逐项验证：

- [ ] 测试环境长连接成功建立。
- [ ] 私聊机器人发送文本后，后端只收到一次事件。
- [ ] 测试群中不 @机器人 的普通消息不会触发。
- [ ] 测试群中 @机器人 后，机器人立即给出 reaction 或“处理中”提示。
- [ ] 最终回复在原 thread 中，而不是群主聊天流。
- [ ] 重放同一 `message_id` 不会创建第二个 Agent 任务。
- [ ] 缺少 `LARK_APP_SECRET` 时服务明确失败或禁用飞书模块，不伪装成正常运行。
- [ ] bot 不在某个群时，出站失败日志能保留飞书错误码和请求日志 ID。

## 11. 明确不在第一阶段做的事

以下内容等消息闭环稳定后再单独设计：

- 读取或创建飞书文档。
- 多维表格任务管理。
- 用户 OAuth 与私有资源访问。
- Agent 自动获取、修改、拉取代码。
- 自动创建 PR、执行代码审查。
- 发送邮件、外联或自动通知。
- 多运行方切换、长会话压缩和跨 Agent 交接。

这些能力都涉及额外权限、审计、确认步骤或不可逆副作用。先完成可靠的飞书消息闭环，再逐项加入工具，风险和排障成本都会低很多。

## 12. 参考原项目时重点查看的文件

后续实现时，建议按顺序阅读以下 Niuma 模块并只借鉴架构，不复制业务配置或凭证：

1. `packages/backend/src/feishu/ws-client.ts`：飞书长连接与事件订阅。
2. `packages/backend/src/feishu/event-router.ts`：私聊/群聊准入、机器人消息过滤。
3. `packages/backend/src/feishu/reactions.ts`：即时 reaction。
4. `packages/backend/src/feishu/reply.ts`：thread 内回复。
5. `packages/backend/src/feishu/niuma-status-card.ts`：处理状态卡片。
6. `packages/backend/src/feishu/niuma-thread-bridge.ts`：运行中消息的 pending 队列与 `/kill`。
7. `packages/backend/src/feishu/niuma-dispatcher.ts`：异步 Agent 派发与失败回收。
8. `packages/backend/src/feishu/user-oauth.ts`：用户 OAuth，仅在需要访问私有资源时参考。

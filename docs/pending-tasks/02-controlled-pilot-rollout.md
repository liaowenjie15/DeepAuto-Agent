## 当前进度

- 已完成可本地验证的 Gateway 准入护栏：试运行配置可暂停新任务，或按工作区、成员和 GitHub 仓库 allowlist 拒绝任务；所有此类决定在创建 Job 前发生，并写入审计。配置提供方可在不重启 Gateway 的情况下切换暂停/恢复状态。实现入口为 `apps/gateway/src/pilot-admission.ts` 与 `apps/gateway/src/dispatcher.ts`。
- 尚未完成 E0 的实际首批范围和责任人确认，也未完成 E1/E2 所需的公网部署、OIDC/应用凭证配置及真实成员、仓库授权。Gateway 只有在宿主显式提供试运行配置时才启用该护栏；部署前必须接入该配置，不能依赖默认行为。

## 目标

在**受限用户、受限工作区、受限仓库和受限任务类型**内，让真实用户从既有入口发起代码任务，并获得可人工审查的 Pull Request 或明确的失败结果。该阶段验证的是控制面、运行面和人工运营能否共同完成一次真实交付；不扩大 Agent 的写入权限。

首期交付仍遵守以下边界：

- 代码修改只能在允许仓库的非默认分支完成，并通过 Pull Request 交付；禁止自动合并、自动部署和直接推送默认分支。
- 高风险动作、批量外部写入、权限变更、密钥操作和宿主机操作一律不进入试运行范围。
- 只启用已完成授权、成员映射和仓库 allowlist 的工作区；未知调用者、资源或工具继续拒绝。
- 固定已验证的 Codex CLI runtime、模型配置和评估基线；运行中不同时引入多 runtime 或新的模型路由策略。

## 非目标

- 不以试运行代替阶段 D 已完成的隔离仓库真实冒烟、失败/超时/无修改验证和固定评估集。
- 不在本阶段接入新的 Git Provider、自动合并/部署、生产数据库写入或飞书高风险写工具。
- 不因单次成功就向全部成员或全部仓库开放；扩大范围必须经过本阶段退出评审。

## 阶段任务

| 编号 | 任务 | 完成标准 |
| --- | --- | --- |
| E0 | 冻结试运行边界与值班责任 | 记录首批工作区、成员、仓库、默认基分支、允许任务类型、并发上限、单任务预算/超时和暂停条件；指定任务受理、PR 审查与故障处置责任人。 |
| E1 | 配置真实运行入口 | 部署受信任隔离仓库中的执行 workflow；配置 Gateway 公网 HTTPS 地址、GitHub Actions OIDC 信任条件、GitHub App 安装和必要的仓库变量/机密。机密只留在控制面或 GitHub Secrets，禁止写入 workflow 输入、仓库变量、日志或本计划。 |
| E2 | 建立最小权限准入 | 为首批成员完成身份映射，为首批仓库完成 allowlist 和分支保护复核；确认机器人只响应显式提及且不会处理自身消息或未授权来源。 |
| E3 | 建立运营控制与可观测性 | 在任务开始、派发、回调、完成、失败、取消和超时时能够按任务、Attempt 和 Execution 关联排查；准备暂停新任务、取消进行中任务、撤销仓库访问和轮换凭证的操作步骤。日志与审计不得包含上游凭证、OIDC token、回调 claim 或用户 OAuth token。 |
| E4 | 执行受控任务批次 | 由首批用户提交预先批准的低风险代码任务。每个任务必须产生可追溯的受理/拒绝结果，并在成功时产生可审查的 Pull Request；失败、超时和取消必须保留可诊断状态且不得留下未授权副作用。 |
| E5 | 人工审查真实交付 | 对每个成功任务审查需求一致性、改动范围、测试结果、权限边界和 PR 元数据；由代码所有者决定是否合并，Agent 不参与合并或部署。对每个失败任务归类为产品、基础设施、模型、权限或用户输入问题。 |
| E6 | 复盘并决定下一步 | 汇总试运行指标、审计抽查和问题清单，形成“保持小范围 / 修复后继续 / 扩大范围 / 暂停”的明确结论。任何扩大范围的决定都必须列出新增用户、仓库或能力及其独立验收条件。 |

## 首批任务选择

试运行任务应当可回滚、影响面小，并且其完成条件能由仓库检查和人工审查判断。每项任务在受理前记录预期修改范围和验收方式。

优先选择：

- 补充或修复已有测试、类型或静态检查问题；
- 修改局部实现、文档或开发工具配置，且不会改变认证、支付、权限或数据迁移行为；
- 有明确复现步骤和预期结果的小型缺陷修复；
- 明确要求“不改代码、只分析”的任务，用于确认只读交付边界。

不得选择：

- 涉及生产凭证、权限模型、默认分支保护、部署配置或数据库迁移的任务；
- 需要批量修改、跨多个未审核仓库修改或绕过现有测试的任务；
- 不能说明验收结果、风险范围或资源归属的开放式请求。

## 每次任务的运行清单

1. **受理前**：确认调用者、工作区、目标仓库、任务类型和基分支均在本阶段允许范围内；不满足任一项即拒绝并保留审计原因。
2. **执行中**：确认同一会话没有并发执行冲突，Execution 有有效时限，且运行日志可由任务标识关联。出现预算、超时、授权或回调异常时停止继续写入。
3. **完成后**：确认成功任务仅提交至专用分支，并提供 Pull Request、提交标识和验证结果；无修改任务不得伪造代码产物。
4. **失败后**：确认 Job、Attempt 和 Execution 的终态一致，必要时取消后续重试；检查不存在遗留分支、未关闭的权限或暴露在日志中的敏感信息。
5. **人工交接**：向发起人说明结果、未完成项和下一步。只有代码所有者在正常仓库流程中批准并合并 Pull Request。

## 试运行度量与退出门槛

开始前为首批任务建立一份不可变的任务清单，并为每项任务保存以下记录：任务来源、授权判定、开始/结束时间、终态、PR 或失败原因、人工审查结论、成本与耗时、异常处置。

阶段结束时必须满足：

- 所有试运行任务都有可追溯终态；不存在无法解释的挂起 Job、Attempt 或 Execution。
- 每个成功任务都有人工审查记录，且所有代码改动均通过 Pull Request 进入仓库流程。
- 拒绝、失败、超时和取消样本均可从审计记录还原原因与处理结果；未发现跨工作区、跨仓库或跨任务的权限越界。
- 试运行期间未发生默认分支直写、自动合并、自动部署、长期凭证泄露或未授权外部写入。
- 实际成功率、人工返工、耗时、成本和失败类型已与阶段 D 的固定评估基线对照；若出现明显回退，先修复并重新验证，不扩大范围。
- 值班责任人已演练暂停入口、撤销访问、取消执行和凭证轮换，并记录演练结果。

## 退出产物

阶段 E 完成后应交付一份试运行复盘，至少包含：

- 实际开放范围与批准依据；
- 任务清单及每项任务的最终状态；
- 审计抽查、PR 审查和安全事件结论；
- 失败分类、根因、修复负责人和关闭条件；
- 与固定评估基线的差异；
- 下一阶段的范围建议，以及继续受限、扩大范围或暂停的决策。

该复盘是扩大范围的唯一输入；在复盘结论获得批准前，首批 allowlist、并发和任务类型不得自行放宽。
